# MQ 项目面试问答预案

## Q1：为什么这个项目的性能验证没有直接用 JMeter？

项目使用的是自定义 TCP 协议和二进制序列化，不是标准 HTTP 接口。直接用 Java 测试脚本复用现有客户端 SDK，更接近真实链路：

- `ConnectionFactory -> Connection -> Channel` 这条链路会真实覆盖协议封包、网络传输和服务端处理
- 能直接复用项目内的数据结构和错误处理逻辑，不需要额外写一层协议适配
- 本轮目标是建立 smoke baseline，而不是做工业级压测平台

如果后续要做更高强度的压测，可以考虑给 JMeter 写自定义 Sampler，或者用 Gatling 的 Java DSL 做协议扩展。

## Q2：你是怎么设计这些测试用例的？

本轮不是按模块“想到什么测什么”，而是按方法论拆的：

- **等价类划分**：Router 的 `bindingKey` 被拆成合法模式和非法模式，例如 `aaa.*` 与 `order.a*`
- **边界值分析**：`MessageFileManager.checkGC()` 的关键条件是 `totalCount > 2000 && validRatio < 0.5`，所以专门卡了 `2000 / 2001` 和 `50%` 这几个边界点
- **状态转换**：`VirtualHost` 的重点不是单个接口，而是 `publish -> consume -> ACK -> durable 清理` 这条状态链
- **异常路径回归**：缺失 exchange、非法 routingKey、缺失消息 ACK 这类负路径必须单独补

这几类方法组合起来，既能覆盖正常流程，也能覆盖最容易漏掉的边界与异常。

## Q3：为什么集成层不用 mock，而是坚持走真实 SQLite 和文件系统？

因为这个项目的核心风险就在持久化一致性上，mock 会把最关键的问题绕过去：

- SQLite 文件锁释放顺序不对，会直接影响测试稳定性和真实行为
- 消息文件的读写删除如果有边界问题，mock 完全测不出来
- `@BeforeEach` / `@AfterEach` 清理顺序不对，会导致跨测试污染

所以本轮集成测试的核心原则是“尽量让真实状态流动起来”，而不是只验证方法有没有被调用。

## Q4：84.60% 的覆盖率怎么看？为什么没有把它吹成“已经足够高”？

84.60% 说明核心业务路径已经被自动化保护住了，但它不等于“系统已经足够健壮”。

剩余 15.40% 未覆盖部分主要集中在三块：

1. `MqApplication.main()` 这种生产入口
2. `BrokerServer` 的网络异常处理分支
3. `ConsumerManager` 的线程池中断 / 异常传播路径

这些路径的共同特点是：要靠故障注入才能稳定覆盖。它们恰恰是生产环境更容易出问题的地方，所以本轮结论应该是“覆盖率接近目标、核心链路可信，但韧性测试还不够”，而不是简单报一个好看的数字。

## Q5：你怎么保证异步测试结果是可信的？

这是这轮测试里专门处理过的点。

如果直接在 Consumer 回调线程里断言，断言失败可能被线程吞掉，主线程却误以为测试通过。为了解决这个问题，测试统一采用：

- `CountDownLatch`：等待事件发生
- `AtomicReference` / `AtomicInteger`：安全保存回调结果
- 主线程断言：让 JUnit 真正接住失败
- 条件稳定等待：负面场景不再靠盲目 `Thread.sleep()`，而是观察一段稳定窗口，确认没有额外消息投递

所以异步测试的可信度来自“结果跨线程传回主线程再断言”，不是来自“回调里看着像成功”。

## Q6：multi-producer 的 TPS 为什么只有 single-producer 的 3.46 倍，不是接近 4 倍？

这反而是更真实的数据。

4 个线程并发发布时，TPS 从 1437.55 提升到 4977.18，说明系统具备明显扩展性；但没有到 4 倍，说明仍然存在共享资源竞争：

- Broker 端存在内存结构、线程调度和持久化写入的共享成本
- 测试规模较小，连接建立与 JVM 抖动对结果影响更明显
- SQLite 和消息文件 I/O 在并发场景下不会线性扩张

所以更合理的表述不是“接近线性扩展”，而是“扩展性明显，但已经能看到共享资源竞争的痕迹”。

## Q7：ACK 场景为什么平均延迟明显高于纯发布？

因为 `publish-consume-ack` 走的是完整链路，而不是单点发布：

- 发布消息
- Consumer 被唤醒并执行回调
- 手动 ACK
- durable 消息从待确认结构和磁盘消息文件中删除

这条链路里同时包含线程调度、内存状态变更和磁盘 I/O，所以平均 4.28 ms/条是可以解释的。它比纯发布场景高约 6.11 倍，说明当前瓶颈主要不在网络，而在“消费确认 + 持久化删除”这一段。

## Q8：如果让你继续做下一轮测试，你会优先补什么？

本小姐会按风险优先级来补，而不是继续堆简单正例：

1. **Broker 重启恢复测试**：验证 SQLite 元数据和消息文件在异常退出后的恢复一致性
2. **网络故障注入**：补 `BrokerServer` 的异常分支
3. **长稳与高并发压测**：观察内存、文件句柄和性能拐点
4. **负路径日志治理**：现在负路径虽然能测，但控制台堆栈太吵，后续应提升日志可读性
